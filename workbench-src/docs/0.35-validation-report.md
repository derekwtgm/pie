## B. Input driver
`desktop/bin/EightMaxInput.exe` (C# 5, .NET Framework 4.x, x64, PerMonitorV2 manifest; sources `desktop/input/*.cs`), built on Windows.
* **APIs (documented only):** `SendInput` (absolute virtual-desktop mouse moves, buttons, virtual-key and Unicode keys), `GetCursorPos`,
  `SetCursorPos` (≤ 2 px final correction only; 0 corrections were needed on Windows), `WindowFromPoint`/`GetAncestor`,
  `GetWindowRect`/`DwmGetWindowAttribute`/`GetClientRect`/`ClientToScreen`, `GetDpiForWindow`/`GetDpiForMonitor`,
  `GetGUIThreadInfo`, `SendMessageTimeout(WM_GETTEXT)`, `SetForegroundWindow` (+ documented `AttachThreadInput` fallback),
  `QueryFullProcessImageName`/`GetProcessTimes`, `RegisterHotKey`, `RegisterRawInputDevices`, UI Automation (read-only: control list,
  focused value). **No hooks, no process-memory access, no injection, no hidden input, no anti-detection, no randomness.**
* **Architecture:** one JSON object per line on stdio, opened by an authenticated `hello` (random 256-bit token in the environment);
  input operations run one at a time on a worker; `cancel`, `estop`, `status`, `release-all` are handled immediately on the reader
  thread; bounded queue (8) with queue timeouts; parent-process watchdog; stdin EOF ends it. The desktop host owns the single driver
  process (`desktop/InputBroker.cs`, job object with kill-on-close, whitelisted commands, `/api/input/*`, no silent restart after a crash).
* **Operations:** move, move-click, click, double-click (only when explicitly authorised for a control), mouse down/up, keys
  (Backspace, Delete, Enter, Escape, Tab, Home, End, arrows), sequential typing, clear-field, read-text, enter-text (click → focus check →
  clear → type → read back), focus, window info, monitors, list windows, executable identity, UI Automation control list, cursor sampler.
* **Authorisation:** input only into windows registered with an `eightmax-simulator-authorization` record (own simulator, test only,
  no real money, ≤ 8 h) bound to the executable's **file name and SHA-256**, checked by the driver itself. Every operation re-checks
  handle + pid + process start time + class, minimised/hidden/cloaked, the expected client rectangle, and that the window under the
  point is the target.

## C. Smooth mouse movement
Minimum-jerk profile s(u) = 10u³ − 15u⁴ + 6u⁵ (zero speed and acceleration at both ends). Duration = the shortest respecting max speed
(peak 1.875 D/T), max acceleration (10/√3 · D/T²), a minimum time and — for the optional deterministic arc — exact bounds for the
curved path. ~60 updates/s (16 ms, `timeBeginPeriod(1)` pacing). A deadline never speeds a movement up: it is refused (`deadline`,
`move-too-long`). Defaults: 1600 px/s, 9000 px/s², 140 ms minimum, 16 ms interval (all user-adjustable). JS mirror `src/input-motion.js`
plans the same pixels (asserted pixel-for-pixel against the C# code).

Windows measurement (run 44773047062, input acceptance, 1,010 px diagonal move): commanded path = the minimum-jerk plan exactly; peak
speed **1600.1 px/s** (limit 1600), peak acceleration **6199 px/s²** (limit 9000); update interval median **15.97 ms** (min 15.73,
max 16.23); planned 1181.8 ms, executed not faster; independent 1 ms cursor sampler: **71 distinct positions, largest step 25.6 px**
(= 1600 px/s × 16 ms; limit 34 px), **target error 0 px**, **0 samples with the button down** during movement; cancel mid-move:
cursor displacement after cancel **0 px**.

## D. Keyboard control and wagers
Typing is key by key (digits and '.' as virtual keys, other characters as Unicode) with configurable interval/hold; focus is verified
before every key (`focus-lost` stops typing — verified: the other window received **0** keystrokes). Wager entry: click the calibrated
field, verify the focused control is that Edit, clear it (End + Backspace × length, bounded wait until empty), type, **read back** and
refuse on any difference (field cleared, nothing submitted). Before typing, `wagerText()` validates integer chips, chip unit, > current
bet, ≥ minimum (except all-in), ≤ maximum/stack, raise availability, and converts **raise-to vs raise-by** (`execution.amountConvention`).
Windows: 450 typed and read back exactly; the table applied a raise to exactly 450; an amount below the minimum was refused by the
table and the state did not change. Benchmark: **0 incorrect wagers** in 414 confirmed actions (section G).

## E. Calibration
Regions are normalised to the client area and converted with the client rectangle the driver reports **right before each action**
(`src/input-geometry.js`: inset click rectangle, centre point, minimum size); the driver refuses if the rectangle differs from the one the
screenshot was taken with (`layout-changed`) — verified on Windows after a move + resize, and fresh coordinates then hit the intended
control. All coordinates are physical pixels (driver and capture are per-monitor-v2 DPI aware), so 150 %, 4K and negative multi-monitor
coordinates need no special case (unit-tested at 1080p, 1440p, 4K, 150 % and a monitor left of the primary). Wizard in the dashboard:
screenshot, drag regions (or UI Automation suggestions), preview with click points / DPI / resolution / confidence, dry run (moves, never
clicks), save/import in the existing checksummed profile format (version unchanged), bound to the simulator executable.
**Not measured:** a real 150 % or 4K display, or more than one monitor (the hosted runner has one 100 % display and cannot change scaling).

## F. Screen-to-action integration
`src/simulator-controls.js`: host capture (PrintWindow) → calibrated reader + status strip → HandStateEngine → decision → TestExecutor
(QA mode, authorisation, freshness, legality, duplicate slot) → UiAutomationAdapter → **scheduler lease** → in-lease revalidation by a
fresh capture (same revision, same rectangle) → driver → captures until the frame changes → `confirmAction`. Outcomes **confirmed,
rejected, ambiguous, timed-out, cancelled**; anything but confirmed pauses the table; visible input is never retried; only a refusal that
provably sent nothing may be retried from a fresh reading (≤ 4 in a row). Decisions here are the **labelled SCRIPTED test policy**,
permitted only on the bundled controlled table (no EightMax strategy covers these random 8-handed spots in a fresh install) — this
measures control reliability, not strategy accuracy. Confirmation latency on Windows: p50 **147–272 ms**.

Every confirmed action was matched against the test table's oracle (same hand, seat, type, amount): **0 incorrect clicks, 0 incorrect
wagers, 0 clicks on old frames, 0 double-clicks, 0 presses outside controls, 0 driver or focus errors, 0 paused tables** in all 20 runs.
The same pattern held in three earlier full benchmark runs (44766260365, 44768740044).
**Realistic limit: 5 tables.** Physical input is serialised; one exclusive lease (revalidation capture, movement, click or typing)
takes ~1 s, so the cursor serves about **60–75 actions per minute in total**. From 8 tables on, a few actions per minute could not be
completed inside the 10 s window at the configured speed and were **refused, not rushed** (counted as missed deadlines); 10 tables
happened to have 0 or 1 such miss per run, which is not a reliable margin. Ten-table operation is therefore **not claimed**; more
tables need a longer decision window, faster (configurable) movement, or fewer typed amounts.

## H. Reliability
Verified on Windows: emergency stop latches (`Ctrl+Alt+F12` through `RegisterHotKey`; dashboard button; queued and new input refused;
cannot re-arm until reset); cancel mid-movement (0 px afterwards); no button or key left held (driver status and `GetAsyncKeyState`);
focus loss stops typing; minimised and closed windows refused; a covered control is refused under `focusPolicy: refuse` or the window is
raised first (only it received the click); manual override available through Raw Input (tested on the virtual desktop: a simulated user
move makes the driver yield until an explicit resume; also cursor-deviation checks between and during operations — on Windows these
correctly caught the self-test's own out-of-band cursor positioning); the driver exits on shutdown (no orphan process). The host restarts
a crashed driver only on request and the new driver starts disarmed. **Not tested with a person** at the keyboard (no human on the runner).

Defects found and fixed during 0.35 work: (1) UI adapter recorded the idempotency key only after the click resolved while the executor
retried on timeouts → a slow click could repeat; (2) the scheduler could start a second lease while the first awaited revalidation
(overlapping input, found by test) and could strand a job submitted as the pump finished; (3) a clean pre-input refusal consumed the
state slot so the table could never act again; (4) **two separate single clicks on one spot within the double-click time arrived as a
double-click** (found on Windows; now spaced beyond `GetDoubleClickTime`); (5) state reconstruction rejected every frame in which
another player is to act with the controls off (normal client behaviour) — confirmation waited for the next turn (~2.5 s) and a
hand-ending action became ambiguous (found by the Windows benchmark; fixed in `src/hand-state.js`, confirmation now ~150 ms);
(6) the driver read the wager field back before the window had processed the keys (seen once on Windows; now a bounded wait);
(7) DPI awareness was mis-reported as "system" because the manifest had already set PerMonitorV2.

## K. Remaining simulator-specific integration
1. **Recognition of your simulator's table** (cards, stacks, pot, buttons lit/unlit): the shipped reader is calibrated for the Workbench's
   own renderer; your simulator needs a recognition calibration for its look (or a status line like the test table's strip).
2. **Hero seat and opponents**: the controller acts only when the screen offers the viewer an action; set your seat on screen in the
   calibration. The test table shows the acting seat's view (self-play).
3. **Amount convention, chip unit, All-in button** of your wager field — set in the calibration.
4. **EightMax decisions for live spots**: automated play on your simulator uses EightMax decisions when a decision source is attached
   (`window.EIGHTMAX_DECIDE` in the dashboard); otherwise the table pauses ("no EightMax decision") — the scripted policy is refused there.
5. Your simulator executable (for the SHA-256 binding) and a run of RUN-035-ACCEPTANCE.cmd on your PC (150 %, 4K).

EightMax 5.1 unchanged (`native/mwcli.exe`, `vendor/eightmax-5.1/`, build id); no CFR, training, checkpoint or solver change. The input
driver does not improve strategy accuracy.
